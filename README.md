# IntelliSwap

### Adaptive Memory Page Compression using Content-Aware Compressor Selection

IntelliSwap is an experimental memory-compression pipeline that explores **adaptive compressor selection for 4 KB memory pages**.

Instead of applying a single compression algorithm to every page, IntelliSwap first analyzes the content characteristics of each memory page and then selects an appropriate compressor between **LZ4** and **Zstandard (Zstd)**.

The project evaluates whether lightweight, content-aware routing can achieve a better compression ratio than always using a single compressor, while avoiding unnecessary compression overhead on pages that are difficult or inefficient to compress.

---

## Overview

Modern operating systems can use compressed memory to reduce memory pressure and delay expensive disk swapping. However, different memory pages have very different data characteristics.

For example:

* Zero-filled pages are highly compressible.
* Random pages are effectively incompressible.
* Text-like pages contain moderate redundancy.
* Repetitive pages can achieve very high compression ratios.

Using the same compressor for every page may therefore be inefficient.

IntelliSwap investigates a simple alternative:

# Phase 1 — Dataset & Feature Extraction

The first phase creates a dataset of **500 memory pages**, each exactly **4096 bytes**, representing four different classes of memory content.

| Page Type  | Count | Description                                     |
| ---------- | ----: | ----------------------------------------------- |
| Zero       |   125 | Mostly zero-filled pages                        |
| Random     |   125 | Randomly generated bytes                        |
| Text       |   125 | Pages generated from real source-code/text data |
| Repetitive |   125 | Highly repetitive data and patterns             |

### Data sources

Text pages are generated from source material obtained from repositories including:

* `torvalds/linux`
* `psf/requests`

Random pages are generated using Python's `os.urandom()`.

Zero pages contain mostly zero bytes, with a small probability of a stray non-zero byte to make the dataset slightly more realistic.

Repetitive pages are generated using a combination of uncompressed image data and synthetic repeating patterns.

---

## Extracted Features

Each page is characterized using three lightweight features.

### 1. Shannon Entropy

Entropy measures the randomness or information density of the page.

```text
0 ≤ entropy ≤ 8
```

Low entropy generally indicates more predictable data, while values close to 8 indicate highly diverse/random byte distributions.

The implementation calculates byte-level Shannon entropy using:

```python
H = -Σ p(x) log₂ p(x)
```

### 2. Zero Ratio

The fraction of bytes whose value is `0`.

```text
zero_ratio = number_of_zero_bytes / total_bytes
```

This is particularly useful for detecting zero-filled or nearly zero-filled pages.

### 3. Run-Length Score

The average length of consecutive identical-byte runs.

A larger value indicates stronger structural repetition.

# Phase 2 — Adaptive Compression Engine

The second phase uses the extracted page features to choose between:

* **LZ4**
* **Zstandard (Zstd)**

Each page is also compressed using both algorithms independently to establish static baselines.

---

## Adaptive Decision Logic

The current routing policy is intentionally lightweight and rule-based:

```python
def choose_compressor(entropy, zero_ratio, run_length_score):
    if zero_ratio > 0.9:
        return "lz4"

    if entropy > 7.0:
        return "lz4"

    return "zstd"
```

The logic can be summarized as:

```text
                     Page Features
                           │
             ┌─────────────┴─────────────┐
             │                           │
       zero_ratio > 0.9            entropy > 7.0
             │                           │
             ▼                           ▼
            LZ4                         LZ4
                                         
                         Otherwise
                            │
                            ▼
                           Zstd
```

### Why these rules?

#### Nearly-zero pages → LZ4

Pages with a very high zero-byte ratio are extremely compressible. The experiment routes them to LZ4 rather than spending additional compression effort with Zstd.

#### High-entropy pages → LZ4

Pages with entropy above approximately `7.0` are close to incompressible. Using a more computationally expensive compressor provides little additional benefit for these pages.

#### Remaining pages → Zstd

Pages with moderate entropy are more likely to contain exploitable redundancy. Zstd is used because it generally provides stronger compression for these types of data.

# Compression Engine

The compression engine measures two primary metrics:

### Compression Ratio

```text
compression ratio =
original size / compressed size
```

A higher value represents greater compression.

### Compression Time

The implementation uses Python's high-resolution performance timer:

```python
time.perf_counter()
```

to measure the time required to compress each page.

---

# Baselines

To determine whether adaptive routing provides a useful trade-off, IntelliSwap evaluates three strategies:

### Adaptive

The compressor is selected using page characteristics.

### LZ4-only

Every page is compressed using LZ4.

### Zstd-only

Every page is compressed using Zstd.

This provides a direct comparison between adaptive routing and fixed compressor selection.

# Results

The repository contains results for **500 pages**, each 4 KB in size.

### Average Compression Ratio

| Strategy  | Average Ratio |
| --------- | ------------: |
| LZ4-only  |        31.691 |
| Adaptive  |    **48.529** |
| Zstd-only |        79.077 |

The adaptive strategy therefore improves substantially over the LZ4-only baseline while using Zstd selectively rather than applying it to every page.

### Adaptive Routing Distribution

| Compressor |   Pages |
| ---------- | ------: |
| LZ4        |     305 |
| Zstd       |     195 |
| **Total**  | **500** |

### Routing by Page Type

| Page Type  | LZ4 | Zstd |
| ---------- | --: | ---: |
| Zero       | 125 |    0 |
| Random     | 125 |    0 |
| Text       |   1 |  124 |
| Repetitive |  54 |   71 |

The routing behavior reflects the content characteristics:

* Zero pages are consistently routed to LZ4.
* Random pages are consistently routed to LZ4.
* Most text pages are routed to Zstd.
* Repetitive pages are split depending on their measured entropy.

> These results are based on the dataset and experiment configuration currently stored in the repository. They should not be interpreted as universal performance characteristics of LZ4, Zstd, or operating-system memory compression.

# Design Goals

IntelliSwap is designed around three main ideas:

### 1. Content Awareness

Different memory pages have different compressibility characteristics. The system uses inexpensive statistical features to identify those differences.

### 2. Lightweight Decision Making

The compressor-selection logic uses simple threshold-based rules rather than a heavyweight machine-learning model.

This keeps the decision process computationally inexpensive.

### 3. Experimental Evaluation

The adaptive strategy is compared against fixed LZ4 and Zstd strategies using the same page dataset, allowing the effect of adaptive routing to be measured directly.

# Limitations

This repository represents an experimental evaluation rather than a production operating-system memory-compression subsystem.

Important limitations include:

* The experiment operates on stored 4 KB page files rather than live OS memory.
* The routing policy is rule-based and manually thresholded.
* Compression measurements are performed from Python rather than inside a kernel-level memory-management subsystem.
* The dataset contains four controlled page categories and may not represent the complete distribution of real application memory.
* Compression timing at 4 KB page granularity can be very small, making timing measurements sensitive to system and runtime conditions.
* The current implementation evaluates compression but does not implement actual swap I/O or page eviction/reclamation.

# Research Question

The central question explored by IntelliSwap is:

> **Can lightweight page-content analysis be used to select compression algorithms dynamically and obtain a better compression trade-off than using a single compressor for all memory pages?**

The current experimental results show that content-aware routing can provide a meaningful improvement over the LZ4-only baseline on the included dataset, while avoiding the need to use Zstd for pages where its additional compression capability provides little benefit.
